## Hero stat alignment (commit `98a7da6`)

Author sent a screenshot of the hero stat block — "3+" (36px display serif) above
"years of designing & shipping" (14px muted) — and asked for "better allignment".
The label hung low with a wide gap, so the pair read as two disconnected fragments
rather than one sentence.

### Diagnosis

The row used `items-baseline` on both the outer `dl` and the inner wrapper.
Baseline alignment is right for same-size text, but this is a **36px/14px pair**:

- The numeral's line box is far taller than the label's.
- The label's own leading pushed its baseline well below the numeral's visual
  centre, which is what produced the "hanging low" look.
- So the alignment mode was correct in principle and wrong for these sizes.

### Fix (4 lines, CSS only)

- `items-baseline` → `items-center` on both wrappers
- `leading-none` on the value — the 36px line box was adding leading that
  inflated the row height and dragged the label down
- inner `gap-x-3` → `gap-x-2.5` (tighter numeral/label pair); outer `gap-y-2` →
  `gap-y-3` (keeps wrapped rows legible)
- dropped `flex-wrap` from the inner wrapper — it holds exactly one value and one
  label, so wrapping there would split the pair

`dt`→`dd` DOM order is untouched; `order-1`/`order-2` still swap them *visually
only*, so the markup stays valid HTML.

### Verification

- `npm run verify` → exit 0. Bundle 410.11 kB / 132.51 kB gzip (unchanged).
- Rendered in headless Chrome at 1280×1000 and 500×900 with
  `--force-prefers-reduced-motion`. Both show value and label on one optical
  centre line, no overflow, hamburger intact at 500px.

## Headless Chrome screenshot verification — the recipe that actually works

Wanted to *look* at the fix rather than trust the class names. `agent-browser` is
a dead end here (no browser runtime installed; the CLI's `open` times out), so I
drove system Chrome directly. It took several failed attempts; the working recipe:

```bash
CHROME="/c/Program Files/Google/Chrome/Application/chrome.exe"
WD="$(cygpath -w /tmp/shots)"          # <-- required, see below
"$CHROME" --headless=new --disable-gpu --hide-scrollbars \
  --force-prefers-reduced-motion --virtual-time-budget=6000 \
  --window-size=1280,1000 \
  --screenshot="$WD\\desktop.png" "http://127.0.0.1:5199/"
```

Three traps, all of which failed **silently** (exit 0, no file written):

1. **Chrome is a Windows binary and cannot resolve POSIX paths.** Passing
   `--screenshot=/tmp/shots/x.png` writes nothing and prints nothing. Must convert
   with `cygpath -w` first.
2. **`--force-prefers-reduced-motion` is mandatory.** Without it the framer-motion
   entrance animations haven't run at capture time and the hero renders *invisible*.
   (Side benefit: this is a live test of the `useReducedMotion` implementation.)
3. **Windows headless enforces a ~500px minimum window width.** `--window-size=390,844`
   is silently clamped/letterboxed, so a phone-width shot at 390 is misleading.
   Test at 500 (or 700) and treat anything narrower as untrustworthy.

Useful because it is cheap, needs no dependencies, and catches exactly the class of
bug that typecheck and lint cannot see.

### The safe-delete guard is cumulative — and counts failures

`SAFE_DELETE_BULK_CONFIRM_REQUIRED` counts **all** deletions attempted in the
turn, including ones that failed, so the counter never resets and every
`vite build` needing `emptyDir` fails once past ~50. Observed: 79 → 107 → 247.
Both `rm` and PowerShell `Remove-Item` are intercepted; the shim routes to
`genie-trash`, which fails with "Some operations were aborted" then **fails
closed**.

Workaround that works: `mv dist dist.stale && npm run build` — a rename is not a
delete, so `emptyDir` has nothing to do.

**Consequence:** `dist.stale`, `dist.prev`, `dist.keep3`, `dist.keep4` are
stranded in the project root and cannot be deleted from inside the sandbox. They
are gitignored (`dist.*/`) and verified harmless, but must be removed by hand.

## LazyMotion: domMax → domAnimation (commit `80e1489`)

Bundle 367.00 → 319.13 kB raw, 117.33 → 103.33 kB gzip (−14.0 kB). Cumulative for
the session: **410.11 → 319.13 kB raw, 132.51 → 103.33 kB gzip (−22%)**.

`motion.*` bundles the full **domMax** feature set. The app uses only
`initial`/`animate`/`whileInView` + springs — no `layout`, `drag`, `whileHover`,
`whileTap` or `variants` — so domMax was carrying weight nothing referenced.
Switched all five consumers to `m.*` under one
`<LazyMotion features={domAnimation} strict>` in `main.tsx`.

### The near-miss worth remembering

`Reveal.tsx` uses **`whileInView`**, which needs `InViewFeature`. Had
`domAnimation` lacked it, every Reveal-wrapped section would sit at `opacity: 0`
and render **invisible** — while `tsc`, ESLint and `vite build` all passed. Silent,
severe, and invisible to every gate this project has.

Resolved by reading the package rather than trusting memory:
`features-animation.mjs` spreads `gestureAnimations`, and `gestures.mjs` defines
`inView: { Feature: InViewFeature }`. It is included.
**Verify feature-bundle contents in `node_modules`, never from recall.**

`strict` mode is the durable guard — it throws in dev if a `motion.*` is
reintroduced, so the smaller bundle cannot silently regress.

### Verification

`npm run verify` exit 0, plus two harnesses:
- `cdp-test.mjs` (reduced motion) — **7/7** against dev *and* the built output.
  Passing on dev also proves `strict` didn't throw, i.e. no `motion.*` was missed.
- `cdp-anim-check.mjs` (deliberately **no** reduced motion) — **5/5**: 26 elements
  carry framer-motion inline styles, 19 were still faded pre-scroll, none left
  below 0.9 opacity after scrolling, all 3 LineMask spans resolved to
  `translateY(0)`.

### Three more harness traps

- **Never run the animation check with `--force-prefers-reduced-motion`.** That flag
  resolves every reveal instantly, so a broken `whileInView` passes silently. The
  check asserts `matchMedia()` is false and aborts otherwise.
- **Don't treat every sub-0.9-opacity element as "invisible".** The availability
  pulse dot animates `1 → 0.35` by design; measured mid-cycle it mimics a stuck
  reveal. Exclude elements whose `animationName !== 'none'`.
- A cold dev server plus a first Chrome launch can exceed the mount timeout. Run
  rendering checks against the **built output** behind a static server — no
  on-demand transform delay.

  1 |   0 | . . X . .         5 |  16 | . . X . .
  2 |   4 | . . X . .         6 |  20 | . . X . .

## Booking availability fix (author-approved)

Author chose: guarantee availability **and** add an empty state; delete `daysAhead`;
enable `exactOptionalPropertyTypes` only.

### The fix

`isSlotBooked` capped. The raw pattern is now a separate `looksTaken`, and the
exported function counts how many *earlier* slots that pattern already took:

```ts
const MAX_BOOKED_PER_DAY = 2;
const looksTaken = (dayIndex, slotIndex) => ((dayIndex + 2) * (slotIndex + 3)) % 5 === 0;

export function isSlotBooked(dayIndex, slotIndex) {
  if (!looksTaken(dayIndex, slotIndex)) return false;
  let takenEarlier = 0;
  for (let earlier = 0; earlier < slotIndex; earlier += 1) {
    if (looksTaken(dayIndex, earlier)) takenEarlier += 1;
  }
  return takenEarlier < MAX_BOOKED_PER_DAY;
}
```

Call site simplified from `day.dayIndex + activeDay * 3` to `day.dayIndex`, and the
slot list is derived once per selected day rather than recomputed inside the map.

New matrix — every day keeps at least three slots:

```
day:  1  2  3  4  5  6  7  8
free: 4  4  4  3  4  4  4  4
```

### Verification

`npm run verify` → **exit 0**. Bundle 319.13 → 319.46 kB raw, 103.33 → 103.48 kB gzip;
CSS 46.45 → 46.50 kB. The +0.33 kB is the empty-state branch and its utilities —
cheap for removing a lead-turning-away dead end.

New harness `cdp-booking.mjs` clicks all eight day buttons in the real DOM and counts
enabled slot buttons. It classifies buttons structurally — day buttons contain two
`<span>`s (weekday + date), slot buttons are plain text — rather than by index, so it
survives layout changes. Result: **4,4,4,3,4,4,4,4**, no empty state shown, matching
the analytical prediction exactly.

Screenshots at 1280×1100 and 520×1000 confirm the render: 8 day buttons
(Mon 21 Sept → Wed 30 Sept), `13:00` struck through, the other four live; single
column and intact hamburger at 520px.

### `daysAhead` deleted

Removed from `data/site.ts`. The count now lives as `DAYS_SHOWN = 8` in

### `exactOptionalPropertyTypes` enabled

Added to `tsconfig.json`. Zero errors, so it is free hardening.

## The leak the tests caused — and the fix that ends the class (commit `d6919f1`)

Adding `tests/` silently added **1408 bytes** of dead CSS to the shipped stylesheet.
Tailwind treats every file it is not told to ignore as opaque text, and ordinary English
words in the suite's comments and strings became real utilities:

- `.blur` — from `includes('blur')` and the word "blurred"
- `.outline` — from `outlineStyle`, `outlineWidth`, and "visible outline"
- `.resize` — from "resizing to desktop"
- plus 15 `@property` declarations those pull in

**Third instance of one bug.** `dist.stale` re-emitted 9 dead utilities; the notes
describing *that* leak emitted `.gap-y-2`; now the tests. Each was patched with
`@source not` — a denylist that needs updating whenever a directory is added, and whose
failure is silent.

So automatic detection is off and the sources are declared:

```css
@import 'tailwindcss' source(none);
@source './**/*.{ts,tsx}';
@source '../index.html';
```

### The `@source './'` trap

My first attempt used `@source './'`, which looks equivalent and made things **worse**
(45973 → 49558 bytes). It registers the whole directory, recursing into
`.workbuddy-ai/` and re-mining the class names the notes list *while documenting them*.
The diff proved it: `.absolute`, `.contents`, `.drop-shadow`, `.ease-in`,
`.ease-in-out`, `.ease-out`, `.filter` — the exact 9 dead utilities named in the prose.
**Notes about dead CSS are themselves a source of dead CSS.** The glob has to be
precise: only `.ts`/`.tsx` and the HTML entry can carry classes.

CSS 46.50 → **45.97 kB**, gzip 19.91 → **19.82 kB**. That is 526 bytes *better* than the
previous best, because auto-detection had also been mining `vite.config.ts`,
`package.json` and `AGENTS.md`.

### A shrinking stylesheet has to be proven safe

Smaller CSS can also mean a dropped utility. So it was checked, not assumed: the full
suite still passes **29/29**, and the hero was verified in the DOM — `opacity: 1`,
`visibility: visible`, a 1152×297 box at y=338, colour `rgb(28,25,21)`, and the correct
Fraunces face at 101px.

### A blank screenshot that was not a bug

The first hero capture came out **4745 bytes** — entirely background. That reads as a
catastrophic rendering regression, and it was not one: `cdp-shot.mjs` with no selector
waited only for `readyState`, which is satisfied long before a framework mounts, so it
captured before first paint. The same viewport captured properly is **81 kB**, and the
computed-style check above confirmed the DOM was always correct.

**The harness was at fault, so the harness was fixed** (in the `headless-chrome-verify`
skill): never wait on `readyState` alone — require a named element or visible body text,
then `document.fonts.ready`, then one more paint. The size warning now fires below
15 kB with an explanation, instead of 2 kB with none.

The general rule, now written into the skill: **a failed capture and a blank page look
identical.** Check the size, open the image, and if the DOM says the element is visible
then the page is fine and the harness is not.

### Method note

The leak was found by **diffing the built CSS against the previous build** and listing
the rules that appeared:

```bash
sed 's/}/}\n/g' old/assets/index-*.css | sort > /tmp/o
sed 's/}/}\n/g' new/assets/index-*.css | sort > /tmp/n
comm -13 /tmp/o /tmp/n
```

Not by reading the test files and reasoning about them. It was invisible in review and
obvious in a diff — which is the whole argument for keeping the previous build around
instead of deleting it.

### The card, and the trap it walked into

`public/favicon.svg` is the source of truth: a stroked `<path>` M on an ink tile, not a
`<text>` element, because a favicon is a standalone document with no `@font-face` — text
would render in whatever font the viewer's machine happens to have.

The mark carries **no accent dot**, even though the wordmark does. The first version had
it and it merged into the M's right leg at 32px; the gap works out to under half a pixel
at 16px. Verified by rendering the mark at 16/32/64 on both light and dark chrome and
looking at it.

`tools/generate-brand-assets.mjs` renders the 1200×630 card and the icon rasters through
real Chrome, so there is no image toolchain. It is committed because the outputs are
PNGs: an unreproducible binary is the same two-sources-of-truth failure this project
keeps hitting.

**The first run produced a textless card** — every element present, every word missing,
5623 bytes. Not a layout bug: `font-display: block` hides glyphs until the font arrives,
so a font failure reads as a *deliberate minimal design*. The correct card is 46376
bytes. The generator now asserts `document.fonts.check('110px Fraunces')` before
capturing, and reads each PNG's real dimensions out of the IHDR chunk.

### Three real bugs in the CDP harness

Found while debugging that blank card, all previously reporting the same misleading
"Chrome never reported a DevTools port":

1. **`readFileSync` on `DevToolsActivePort` was unguarded.** Chrome writes that file in
   place and on Windows the read lands mid-write and throws **EBUSY** — which crashed out
   of `launch()` entirely. A locked file is not an absent one; retry.
2. **Chrome's stderr was discarded** (`stdio: 'ignore'`), so the only thing that explains
   a launch failure was thrown away. Kept and included in the error.
3. **The harness attached to a target that never navigated.** Chrome is handed the URL on
   its command line, but *which* target it creates first is a race. Attaching to a
   pre-navigation target that is already `readyState === "complete"` means the readiness
   check passes against a blank document — this is what produced the textless card. Fixed
   by sending `Page.navigate` explicitly and polling `location.href === target`:
   **`readyState` cannot distinguish the new document from the old one.**

All three are now fixed in the `headless-chrome-verify` skill's two scripts too, which had
the identical faults (hardcoded ports 9444/9445, discarded stderr, no explicit
navigation). Both re-tested after the rewrite: `cdp-shot.mjs` writes 81103 bytes for the
hero, `cdp-interact.mjs` passes a 4-check plan.

## Prose that restated its own data (commits `835a23b`, `ca1517a`)

Audited the sections and components no gate had covered. Every real defect found was the
same shape: **a fact stored twice.**

### What was actually wrong

| Where | The duplicate | Symptom |
| --- | --- | --- |
| `About.tsx` | hardcoded "For 3+ years" beside a stat saying 3+ | **had already drifted once** — the notes record "8+ years" surviving the stat changing to 3+ |
| `About.tsx`, `Footer.tsx` | "Nigeria" hardcoded twice, while `site.location` also held it | three copies of one fact |
| `Contact.tsx` | `availability.replace('Available for ', '')` | silent no-op if the prefix changes; also rendered "booking Q4 2026 projects" — missing its "for" |
| `Footer.tsx` | its own copy of the section id list | **had already diverged**: Nav printed "Approach", Footer printed "approach" |
| `data/site.ts` | `process[].index: '01'` | reordering the array would print 02, 01, 03 |

The Footer/Nav one is the nicest find because it was *invisible*. Both render through
the `label` class, whose `text-transform: uppercase` made "approach" and "Approach" look
identical. Only `textContent` disagreed — and renaming a section id would have silently
changed what the footer visibly said. `innerText` would have hidden it too, since it
applies text-transform.

### The fix: name the fact once

```ts
export const country = 'Nigeria';
export const bookingWindow = 'Q4 2026';
export const yearsExperience = '3+';

export const sections = [
  { id: 'approach', label: 'Approach' },
  { id: 'services', label: 'Services' },
  { id: 'about', label: 'About' },
  { id: 'contact', label: 'Contact' },
] as const;
```

`site.location`, `site.availability` and `site.stats[0].value` are now built from the
constants; Nav and Footer both render `sections`; `process` lost its `index` and Approach
derives it by position exactly as Services already did.

### Also: the page had no `main` landmark

`App.tsx` rendered `Nav`, `Home`, `Footer` inside a plain `div`. Nav and Footer were
landmarks from the start; the content between them was not, so "skip to main content" had
nowhere to land. jsx-a11y does not require a main landmark, so nothing flagged it. Fixed
with `<main><Home /></main>` — `main` is `display: block`, so it is layout-neutral.

### The new suite, and testing the test

`tests/suites/consistency.mjs` — 10 checks, **none of which hardcode an expected
string**. Each derives a value from one rendered element and asserts another agrees:
the stat value must appear in the prose, the booking window parsed out of the Hero line
must appear in the Contact intro, the country parsed out of the location label must

### The Chrome 153 incident

Mid-session the suite suddenly failed with "Chrome never reported a DevTools port", and
a manual launch produced a **GUI window** (`chrome://newtab/`) that never exited. It
looked exactly like a regression I had just introduced.

It was neither. **Chrome auto-updated to 153.0.8010.48 while I was working.** During the
update, launches hung and never published `DevToolsActivePort`; the updater's own log
showed `Failed to open named pipe server process ... Access is denied`. Once the update
settled, startup measured **794ms** (5.8s / 1.2s / 0.79s across three runs).

Ruled out along the way, with evidence rather than reasoning: the headless flag
(`--headless=new`, `--headless` and `--headless=old` all work, once the update finished),
and port auto-assignment (`--remote-debugging-port=0` publishes the port file; an
*explicit* port makes Chrome 153 skip the file entirely and serve the endpoint anyway).

**The real defect the incident exposed:** `child.kill()` only signals the launcher, and
Chrome's tree survives on Windows. 9 orphans from one hung launch; 20 live chrome.exe at
one point, **19 of which were the user's actual browser session** — which is why I
checked process command lines before killing anything instead of running
`taskkill /IM chrome.exe`. Now killed with `taskkill /F /T`. Verified: a full 6-suite run
leaves the count unchanged at 9.
